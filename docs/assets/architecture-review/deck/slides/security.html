Security model

Safety comes from credentials and code, not the prompt

ThreatMitigation
A malicious PR steals a tokenTwo jobs: read-only with the model key, or write with no secret
A fork PR runs with secretsThe gate stops forks before checkout; no secret is used
Injection via the PR descriptionTitle, description, branch, and commits never reach the model
Injection via code or requirementRandom-suffix data blocks; a tripwire outside the model
A false finding or a false “yes”Provenance checks drop it; an unproven “yes” becomes “partly”
Exfiltration through toolsRead-only tools, checkout only, keys and .env files excluded
Markup or pings in the outputEscaping, @ mentions neutralized, length caps

Residual risk: the diff, changed files, and Jira text go to a third-party model provider, whose data handling each adopter must accept.

ADR-001, ADR-002, ADR-006 · actions pinned by commit SHA · Jira is GET-only · 15

The design assumes that every word in the pull request and the requirement is attacker-controlled and that the model can be talked into anything. So the guarantees come from outside the model: credential separation between the jobs, a gate that never runs fork code with secrets, a data boundary that keeps the PR’s own text out of the prompt and fences everything else in random-suffix tags, deterministic validation of every finding, escaping of everything published, and logs that hold only identifiers, counts, states, hashes and HTTP statuses. Only users with admin, maintain or write permission can start a review by comment, which also limits cost abuse.
