Reading the PR

The diff comes from the API; the code comes from a checkout

1 · GitHub API

GET /pulls/{n}/files, 100 per page: path, status and patch. DiffMap marks which lines the PR changed.

2 · Checkout at head SHA

Changed files read from disk, UTF-8 text only, numbered “N: text”; the job first checks the PR did not move.

3 · Tools during the review

read_file, search and list_dir over the same checkout: callers and conventions, not only PR files.

4 · Validation re-reads

Each finding’s line must exist in its file at the head SHA, or it is dropped.

Before anything reaches the model: PathGuard drops .env*, keys, lockfiles, binaries, *.min.* and the exclude input; past 400,000 characters a file becomes a placeholder and coverage is incomplete.

GitHubClient.GetPullRequestFilesAsync · RepositoryTools · PathGuard · ContextBudget · 9

The review job checks out the repository at the pull request’s head SHA and, right after, re-reads the pull request: if a commit arrived meanwhile, the job stops and asks for a new review. GitHub returns no patch for binary or very large diffs, and those files are sent without one. A file with a NUL byte in its first 8,000 bytes is treated as binary and skipped. Removed files are not sent. Every patch and every file draws from the same 400,000-character budget the tools use; what does not fit is replaced by a note saying why, and the coverage becomes incomplete with the reason “context budget reached”.
